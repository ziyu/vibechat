# 文档分类、生命周期与维护规范

> 文档类型：治理规则
> 状态：生效
> 更新日期：2026-08-11

## 1. 模型边界

内容文档只有三个生命周期状态：开发中、长期稳定、已归档。`docs/governance/` 是定义和执行规则的控制区，不是第四个生命周期状态。

## 2. 三个内容生命周期

### 开发中

适用于路线、RFC、调研、迁移方案、实施记录和仍需验证的操作说明。开发中文档可以快速演进，但必须标明完成条件，不得被引用为已承诺的长期契约。

### 长期稳定

适用于已核验并持续维护的设计、Runbook、参考资料、发布说明和计划。稳定不代表所有内容都是设计，也不代表永不变化；文档类型决定正文回答的问题。

### 已归档

适用于已被替代、已完成、已取消或与当前代码不一致的内容。归档后不继续修正文义；只允许补充归档说明、替代链接或必要的安全警告。

## 3. 文档治理控制区

`docs/governance/` 保存分类规则、模板、写作约定、质量门槛、索引和迁移台账。这里的文件使用“文档类型”和“状态”描述，不填写内容生命周期，也不参与“开发中 → 长期稳定 → 已归档”的流转。

治理规则变更时，应检查入口、模板和自动化是否仍然一致。

## 4. 稳定文档类型

生命周期表示内容成熟度，文档类型表示正文用途，两者是两个独立维度。进入 `docs/stable/` 的正文必须选择一种类型：

| 类型 | 目录 | 必须回答的问题 | 必备内容 |
| --- | --- | --- | --- |
| 设计 | `stable/designs/` | 为什么这样做，边界和取舍是什么 | 目标、非目标、架构、不变量、变更要求 |
| Runbook | `stable/runbooks/` | 如何可靠完成一项操作 | 前置条件、步骤、验证、故障处理 |
| 参考资料 | `stable/references/` | 有哪些参数、接口或兼容性事实 | 范围、结构化查表信息、来源、更新时间 |
| 发布说明 | `stable/release-notes/` | 某次已经交付了什么 | 交付内容、兼容性/迁移、安全或账务影响、相关文档 |
| 计划 | `stable/plans/` | 当前认可的目标和先后顺序是什么 | 阶段、范围、完成标准、依赖与非承诺项 |

目录 `README.md` 只承担导航，是结构索引，不作为第六种内容类型，也不需要内容生命周期元数据。

### 稳定设计的 Active 实施伴随文档

稳定设计描述尚未完成的目标状态时，应在 `docs/development/active/` 建立实施伴随文档，并双向链接：

- 稳定设计保存目标、边界和不变量，不记录每日开发进度。
- Active 文档保存当前状态、工作流、差距、待决策项、完成条件和实现证据。
- `active` 是开发中生命周期里的状态视图，不是生命周期或文档类型。
- 没有代码、测试或运行证据的工作不能在 Active 文档中标记为 Complete。

## 5. 内容状态流转

```text
开发中 ──核验通过──> 长期稳定
   │                       │
   ├──取消/过期──────────> │
   │                       │
   └──────────────────────> 已归档
                           ▲
长期稳定 ──被替代─────────┘
```

归档内容不能直接恢复为长期稳定。需要恢复时，先复制必要事实到新的开发中文档并重新核验，再按正确类型迁入稳定区。

## 6. 最小元数据

新建或实质修改的内容文档应在标题后提供：

```markdown
> 生命周期：开发中 / 长期稳定 / 已归档
> 状态：草案 / 评审中 / 生效 / 已归档
> 更新日期：YYYY-MM-DD
> 维护范围：涉及的应用、库或业务域
```

开发中文档还应说明完成条件；归档文档应说明归档原因和替代文档（如有）。

治理文件不使用上述生命周期字段，改为填写：

```markdown
> 文档类型：治理规则 / 迁移记录 / 模板
> 状态：草案 / 生效 / 废止
> 更新日期：YYYY-MM-DD
```

## 7. 目录与命名

- 文件和目录使用小写 kebab-case；入口文件使用 `README.md`。
- 内容文档按生命周期放置；稳定文档再按 `designs`、`runbooks`、`references`、`release-notes`、`plans` 分型。治理文件直接放在 `docs/governance/`。
- 不用 `final`、`latest`、`new`、`v2-final` 等无法长期解释的名称。
- 一次性调查材料可以按主题命名；只有确有并行版本时才在文件名中加入日期或版本。

## 8. 单一事实来源

- 稳定事实按类型以 `docs/stable/` 为准：设计解释边界和取舍，Runbook 规定可执行步骤，参考资料提供查表信息，发布说明记录版本事实，计划描述仍有效的目标与顺序。
- 草案计划与待定结论以 `docs/development/` 为准；已核验且持续维护的路线计划放在 `docs/stable/plans/`。
- 发布到站点的用户内容以 `apps/docs-app/content/` 为准，但不得自行定义与稳定设计冲突的产品契约或与稳定 Runbook 冲突的操作步骤。
- 包 API 与局部约束以包内 README、AGENTS 和代码为准。
- 不复制长段正文；使用链接和简短摘要建立导航。

## 9. 评审清单

提交文档变更前确认：

- 分类和状态正确，标题能独立表达主题。
- 范围、非目标、前置条件和完成条件清楚。
- 所有仓库内链接使用相对路径并能解析。
- 命令、文件路径、配置键和示例与当前代码一致。
- 没有把密钥、内部地址、个人数据或供应商控制台数据写入仓库。
- 修改稳定文档时，相关开发提案、类型索引和迁移记录已经同步。

## 10. 维护节奏

- 功能开发时同步更新对应开发中文档和公开用户内容。
- 每次里程碑结束时清理完成或失效的开发中文档。
- 每季度复核稳定文档的适用范围、代码路径与外部依赖。
- 发现错误文档时，优先降级到开发中或归档，不让可疑内容继续以稳定状态存在。
